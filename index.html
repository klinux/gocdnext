Why another CI tool

We loved GoCD's model. We didn't love its stack.

The explicit stage → job → task shape, dependency materials and the Value Stream Map were ahead of their time. The runtime underneath them wasn't.

gocdnext keeps the model and rebuilds everything else: container-native execution, webhook-first triggering, a real plugin catalog, and a UI that reflects the graph you actually run. This is what GoCD would look like if you started it today.

The trade we rejected

  • ✗ Java / Spring / Hibernate → single Go binary per role
  • ✗ XML config → declarative .gocdnext/ YAML, validated by the CLI
  • ✗ Poll-first → webhook-first, auto-registered on GitHub / GitLab / Bitbucket
  • ✗ No marketplace → 60+ versioned plugin images with typed inputs
  • ✗ Rails-era UI → Next.js 15 with a live VSM
What sets it apart

Primitives other CI tools make you bolt on.

Every one of these is first-class in the model — not a plugin, a webhook hack or a convention you have to police yourself.

Upstream material fanout

A pipeline waits for another's stage to pass with the same commit SHA, then fans out to every downstream automatically. No drift, no re-triggering.

Value Stream Map

See the whole graph of pipelines and materials — not a single pipeline's steps, but how a commit flows across every pipeline it touches.

Webhook-first

Push triggers a run instantly; polling is only a fallback. Create a git material and the webhook auto-registers on GitHub, GitLab or Bitbucket.

Plugin catalog

60+ reference plugins for build, test, scan, sign, deploy, migrate and notify — each a versioned container image with a typed input contract.

Kubernetes-native runtime

Pod-per-job execution with runner profiles (K1–K4), node_selector / tolerations scheduling — or classic Docker on the agent host.

Keyless cloud auth

Jobs mint short-lived OIDC id_tokens: and federate them for cloud credentials — no static service-account keys living in your secrets.

Deployment tracking + rollback

deploy: markers record version-per-environment with history. One-click rollback reuses the prior revision's immutable outputs.

Approval gates

Gate stages on approver groups with quorum (incl. PR-label-driven quorum_by_label), fully audited — and zero compute held while waiting.

Run it locally

gocdnext run-local executes a real pipeline on your machine before you push — same dispatch path as the server.

Pipeline services

Sibling service containers (postgres, redis…) declared in YAML, reachable by every job via DNS alias and drawn as nodes in the graph.

Pipeline as code

A .gocdnext/ folder in your repo.

  • Explicit stage → job → task
    The GoCD shape, in YAML. Nothing implicit about ordering.
  • Dependency materials
    upstream: binds a run to another pipeline's exact revision.
  • Validated before you push
    gocdnext validate catches the error at your desk, not in CI.
.gocdnext/web.yaml
1pipeline: web
2materials:
3  - git: git@github.com:acme/web.git
4    on: [push, pull_request]
5  # wait for api's build on the SAME sha
6  - upstream: api
7    stage: build
8
9stages:
10  - name: test
11    jobs:
12      - name: unit
13        plugin: gocdnext/node@3
14        with: { run: "pnpm test" }
15  - name: ship
16    approval:
17      approver_groups: [platform-sre]
18      required: 2
19    jobs:
20      - name: deploy
21        deploy: { target: prod }

Quick start

Up and running with hot reload.

make dev brings up postgres, minio, server, agent and web behind one foreground process. Ctrl+C tears it all down.

Prefer zero local setup? Open it in GitHub Codespaces or Gitpod — both give public URLs so real webhooks land during development.

Local dev guide →
bash 
# 1. one-shot env scaffold (.env + air, goose, sqlc, buf)
make env-setup

# 2. bring up the full stack with hot reload
make dev

  ✓ postgres  ready on :5432
  ✓ server    api   on :8153
  ✓ agent     gRPC  on :8154
  ✓ web       UI    on :3000
