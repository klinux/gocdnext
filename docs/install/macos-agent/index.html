macOS agent

iOS builds require Xcode, so they must run on a macOS host. gocdnext does not try to put Xcode in a container: the native agent uses the existing shell engine and executes a pipeline’s script: directly on the Mac. Jobs select it with agent tags such as macos and arm64.

The release publishes native agents for Apple Silicon (darwin/arm64) and Intel (darwin/amd64). The installer selects the host architecture, verifies the release’s keyless Cosign signature and checksum, and installs a launchd system service that runs as an unprivileged macOS account.

Before you install

Section titled “Before you install”

You need:

  • a supported Mac with a non-root account dedicated to builds;
  • cosign (brew install cosign);
  • private network reachability from the Mac to the server’s gRPC port (8154);
  • an agent registration token.

The installer verifies the release with cosign verify-blob, which checks Sigstore’s Rekor transparency log. The Mac therefore needs outbound HTTPS to the public Sigstore/Rekor endpoints during installation. An air-gapped Mac cannot run the installer as-is — prepare it separately (mirror the release assets and verify against an offline Rekor bundle, or verify the signed checksums.txt on a connected host and copy the vetted binary over).

The agent connection currently uses plaintext gRPC. Keep port 8154 on a private network or VPN; do not expose it directly to the internet. The HTTP ingress used for the dashboard is not a substitute for this private gRPC route.

For the simplest registration path, enable agent auto-registration on the server and use the same high-entropy token on the Mac:

This is a shared fleet credential: any machine that has it can become a worker. Deployments that need a distinct credential per agent should leave auto-registration off and pre-provision the Mac’s exact name and token through their operator/database workflow.

Install the service

Section titled “Install the service”

Download the installer and the signed checksums, then authenticate the installer before running it. The script Cosign-verifies the binary it installs, but that self-check cannot vouch for the script itself — verify its hash here first, or you would be executing unauthenticated code (that may call sudo):

Supply the non-secret settings, then read the token without putting it in shell history or process arguments:

Set GOCDNEXT_RUN_USER if the service should run as an account other than the user invoking the installer. The default tags are macos,arm64 or macos,amd64, based on the machine. Capacity defaults to 1 because Xcode archives are resource-heavy.

The installer creates:

Path Purpose
/usr/local/bin/gocdnext-agent Signed-checksum-verified native binary
/Library/LaunchDaemons/io.gocdnext.agent.plist Root-owned service definition; contains no token
/Library/Application Support/gocdnext/agent.env Agent settings and token, owned by the build account, mode 0600
/Library/Application Support/gocdnext/workspaces Default checkout/workspace root
/Library/Application Support/gocdnext/logs Service stdout and stderr

The LaunchDaemon is system-managed but its UserName is the unprivileged build account. GOCDNEXT_AGENT_ENGINE=shell is pinned in agent.env; no job container is involved.

Upgrade, reconfigure, or remove

Section titled “Upgrade, reconfigure, or remove”

Re-run the installer with a new GOCDNEXT_VERSION or settings. It replaces the binary and configuration atomically enough for launchd, then restarts the service. Keep the same token for an already-registered name unless you also rotate that agent’s stored token server-side.

Log growth

Section titled “Log growth”

launchd writes the agent’s stdout/stderr to /Library/Application Support/gocdnext/logs/agent.log and agent.err.log. These grow unbounded — the installer does not rotate them.

Rotating them is not a simple drop-in newsyslog rule: launchd holds StandardOutPath/StandardErrorPath as open file descriptors, so renaming the file on disk does not make the running agent reopen the path — it keeps writing to the archived inode. Any rotation must make the service reopen its log files, e.g. truncate/rotate during a maintenance window and then restart the service so launchd reopens the paths:

A validated rotation recipe will be added after the real-Mac smoke confirms the reopen behaviour. Until then, size the disk accordingly or truncate the logs during a drain window.

Stopping and draining

Section titled “Stopping and draining”

KeepAlive is set to SuccessfulExit=false: the daemon restarts on a crash or lost connection, but a clean exit 0 (graceful drain on SIGTERM, see agent drain) leaves it stopped.
